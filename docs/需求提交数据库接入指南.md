# 需求提交数据库接入指南

## 1. 目标

把网站“提交需求”表单从当前的前端成功提示，改为真正写入数据库。

推荐方案：

- 数据库：Cloudflare D1（兼容 SQLite）
- 数据访问：Drizzle ORM
- 提交接口：`POST /api/requirements`
- 数据表：`requirements`
- 部署方式：继续使用当前项目的 Sites 托管流程

完成后，只有数据库成功写入，页面才显示“需求已记录”；写入失败时保留用户已填写的内容，并提示稍后重试。

## 2. 当前状态

目前表单并没有保存数据：

- `app/components/ContactForm.tsx` 的提交函数只执行了 `event.preventDefault()` 和 `setSent(true)`。
- 没有请求后端接口。
- `db/schema.ts` 还没有定义任何数据表。
- `.openai/hosting.json` 中的 `d1` 仍为 `null`，尚未启用 D1。

因此，目前页面上的“需求已记录”只是浏览器中的临时状态，刷新后就会消失，团队也无法在后台查看。

## 3. 建议记录哪些字段

建议为每一条需求保存以下内容：

| 字段 | 类型 | 是否必填 | 用途 |
| --- | --- | --- | --- |
| `id` | 整数 | 自动生成 | 需求唯一编号 |
| `name` | 文本 | 是 | 客户称呼 |
| `company` | 文本 | 否 | 公司或团队 |
| `contact` | 文本 | 是 | 手机、微信或邮箱 |
| `expected_launch` | 文本 | 否 | 期望上线时间 |
| `services` | JSON 文本 | 否 | 多选的服务类型 |
| `budget` | 文本 | 否 | 预算范围 |
| `message` | 文本 | 是 | 项目描述 |
| `status` | 文本 | 自动生成 | 跟进状态，默认 `new` |
| `created_at` | 时间 | 自动生成 | 提交时间 |

不建议默认记录用户的原始 IP、浏览器指纹等信息。如果后续确实需要防刷，应优先使用限流、验证码或不可逆哈希，避免额外收集不必要的个人信息。

## 4. 实施步骤

### 第一步：启用 D1 绑定

修改 `.openai/hosting.json`：

```json
{
  "project_id": "保留当前值",
  "d1": "DB",
  "r2": null
}
```

这里的 `DB` 是代码中使用的逻辑绑定名。实际的 Cloudflare 数据库资源及部署绑定由 Sites 托管平台管理，不需要另外创建 `wrangler.jsonc`，也不要把真实数据库 ID 写进仓库。

### 第二步：定义需求表

在 `db/schema.ts` 中定义 `requirements` 表。建议结构如下：

```ts
import { sql } from "drizzle-orm";
import { index, integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const requirements = sqliteTable(
  "requirements",
  {
    id: integer("id").primaryKey({ autoIncrement: true }),
    name: text("name").notNull(),
    company: text("company"),
    contact: text("contact").notNull(),
    expectedLaunch: text("expected_launch"),
    services: text("services", { mode: "json" })
      .$type<string[]>()
      .notNull()
      .default([]),
    budget: text("budget"),
    message: text("message").notNull(),
    status: text("status", {
      enum: ["new", "contacted", "closed"],
    })
      .notNull()
      .default("new"),
    createdAt: text("created_at")
      .notNull()
      .default(sql`CURRENT_TIMESTAMP`),
  },
  (table) => [
    index("requirements_created_at_idx").on(table.createdAt),
    index("requirements_status_idx").on(table.status),
  ],
);
```

状态含义：

- `new`：新提交、尚未联系
- `contacted`：已经联系
- `closed`：已完成或不再跟进

### 第三步：生成数据库迁移

修改表结构后执行：

```bash
pnpm run db:generate
```

执行后应在 `drizzle/` 下生成新的 `.sql` 文件。需要检查 SQL 是否包含：

- 创建 `requirements` 表
- 创建提交时间索引
- 创建状态索引

迁移文件必须提交到代码仓库，部署时平台才能把表结构应用到真实 D1 数据库。

后续任何字段变更也应修改 `db/schema.ts`，重新生成新的迁移；不要直接在线上数据库里手工改表，否则代码结构和真实数据库会不一致。

### 第四步：新增提交接口

新增文件：

```text
app/api/requirements/route.ts
```

接口职责：

1. 读取 JSON 请求体。
2. 清理字符串前后的空格。
3. 校验必填字段及长度。
4. 校验 `services` 是字符串数组。
5. 通过 `getDb()` 和 Drizzle 写入 `requirements` 表。
6. 成功时返回 HTTP `201` 和新记录的 `id`。
7. 失败时返回适当状态码，但不要向浏览器暴露数据库错误详情。

建议请求格式：

```json
{
  "name": "张三",
  "company": "示例科技",
  "contact": "zhangsan@example.com",
  "expectedLaunch": "1—3 个月",
  "services": ["企业官网", "AI 工作流"],
  "budget": "8—20 万",
  "message": "希望建设一套对外官网和内部内容生产流程。"
}
```

建议响应格式：

```json
{
  "ok": true,
  "id": 123
}
```

最低限度的服务端校验建议：

| 字段 | 规则 |
| --- | --- |
| `name` | 必填，1～80 个字符 |
| `company` | 可选，最多 120 个字符 |
| `contact` | 必填，1～200 个字符 |
| `expectedLaunch` | 可选，只接受表单已有选项 |
| `services` | 最多 6 项，只接受表单已有选项 |
| `budget` | 可选，只接受表单已有选项 |
| `message` | 必填，10～5000 个字符 |

不能只依赖浏览器表单的 `required` 属性，因为任何人都可以绕过前端直接调用接口。

### 第五步：让前端真正调用接口

修改 `app/components/ContactForm.tsx`：

1. 把 `submit` 改为异步函数。
2. 使用 `FormData` 读取字段。
3. 使用 `formData.getAll("service")` 读取多选服务。
4. 调用 `fetch("/api/requirements", { method: "POST", ... })`。
5. 只有接口返回成功后才调用 `setSent(true)`。
6. 提交期间禁用按钮，避免重复提交。
7. 失败时显示明确的错误提示。
8. 请求失败时不要清空表单。

核心调用方式：

```ts
const response = await fetch("/api/requirements", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify(payload),
});

if (!response.ok) {
  throw new Error("提交失败");
}

setSent(true);
```

前端至少需要三个状态：

```ts
const [sent, setSent] = useState(false);
const [submitting, setSubmitting] = useState(false);
const [error, setError] = useState("");
```

按钮文案可以在提交期间显示“正在提交…”。成功后可以保留“再提交一条”的入口，但点击后应重置成功状态和表单。

### 第六步：增加防重复和防滥用措施

公开表单上线前，建议至少完成：

- 服务端字段长度限制和选项白名单。
- 提交按钮 loading 状态，阻止用户连续点击。
- 添加一个普通用户不可见的蜜罐字段；该字段有值时拒绝提交。
- 对短时间内的大量请求做限流。
- 返回通用错误信息，不把 SQL、表名、堆栈等内部信息暴露给用户。

如果垃圾提交仍然较多，再接入 Cloudflare Turnstile。验证码属于增强项，不应替代服务端校验和限流。

## 5. 如何查看和处理提交记录

仅写入数据库还不等于团队会及时看到新需求，建议分两个阶段处理。

### 第一阶段：数据库记录

先完成本指南的表单写入功能，确保所有需求可靠保存到 D1。团队可以通过托管平台提供的数据库管理能力查看记录。

### 第二阶段：通知或管理后台

根据实际工作方式选择其中一种：

- 新需求写入成功后，调用邮件服务通知指定邮箱。
- 写入成功后，发送到团队使用的消息工具。
- 增加一个受身份验证保护的需求管理页面，支持查看、搜索和修改 `status`。

不建议创建一个公开的 `GET /api/requirements` 接口，因为记录中含有联系方式和项目描述。任何查询列表、查看详情、导出或修改状态的接口都必须先做服务端身份与权限检查。

## 6. 本地验证清单

启动开发环境：

```bash
pnpm run dev
```

至少验证以下场景：

- 正常填写后能成功提交。
- 数据库中出现一条字段完整的新记录。
- 多个服务类型都能正确保存。
- 缺少称呼、联系方式或项目描述时无法写入。
- 字段过长或选项被篡改时，接口返回 `400`。
- 连续点击提交按钮不会产生重复记录。
- 数据库写入失败时页面不显示“需求已记录”。
- 写入失败后用户填写的内容仍然保留。
- 页面刷新后，已写入的数据仍存在于 D1。

然后执行项目检查：

```bash
pnpm run build
pnpm test
```

如果修改了数据库结构，还要确认生成的迁移文件已包含在待提交变更中。

## 7. 部署步骤

1. 确认 `.openai/hosting.json` 的 `project_id` 保持不变，`d1` 设置为 `DB`。
2. 确认 `drizzle/` 下存在本次生成的迁移 SQL。
3. 确认构建和测试通过。
4. 通过当前项目的 Sites 流程保存新版本并部署。
5. 部署完成后，在正式网站提交一条明显标注为测试的数据。
6. 在 D1 中确认测试记录存在且字段正确。
7. 删除测试记录或将其状态标记为已关闭。

这个项目不使用 `wrangler.jsonc`，不应改成独立的 `wrangler deploy` 流程。

## 8. 推荐实施顺序

按以下顺序推进，最容易定位问题：

- [ ] 将 D1 逻辑绑定设为 `DB`
- [ ] 在 `db/schema.ts` 定义 `requirements` 表
- [ ] 生成并检查 Drizzle 迁移
- [ ] 实现 `POST /api/requirements`
- [ ] 修改 `ContactForm` 调用接口
- [ ] 增加 loading、错误提示和重复提交保护
- [ ] 增加服务端校验、蜜罐和限流
- [ ] 验证数据库中的真实记录
- [ ] 构建、测试并部署
- [ ] 增加邮件或消息通知
- [ ] 视需要建设受保护的需求管理页面

## 9. 完成标准

满足以下条件即可认为数据库接入完成：

- 提交成功的需求都能在 D1 中查询到。
- 数据库失败时前端不会误报成功。
- 非法数据不会写入数据库。
- 公开接口不能读取或导出已有需求。
- 联系方式等敏感字段不会出现在日志、报错或公开页面中。
- 数据库迁移可以随新版本稳定部署。
- 团队知道在哪里查看新需求，或能收到新需求通知。
